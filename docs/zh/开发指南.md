# 1 a2a-t-sdk-java 开发指南

## 1.1 特性介绍

见[用户指南 1.1特性介绍](https://github.com/project-openan/a2a-t-sdk-java/blob/main/docs/zh/%E7%94%A8%E6%88%B7%E6%8C%87%E5%8D%97.md#11-%E7%89%B9%E6%80%A7%E4%BB%8B%E7%BB%8D)章节。

## 1.2 约束与限制

1. JDK 要求为 17+。
2. 当前支持 `classpath` 和 `local_file` 提示词资源，默认从 jar 内置资源加载。
3. 默认支持 `openai` LLM provider。
4. 协商状态存储当前支持 `in_memory`。
5. SDK 不负责启动业务 HTTP 服务、用户认证、密钥管理和注册中心部署。

```xml
        <dependency>

            <version>1.0.0</version>

            <scope>import</scope>

    </dependencies>
```

```xml
<dependency>
    <groupId>net.openan.a2a-t.sdk</groupId>
    <artifactId>a2a-t-client</artifactId>
</dependency>
```

服务端 Agent 引用：

```xml
<dependency>
    <groupId>net.openan.a2a-t.sdk</groupId>
    <artifactId>a2a-t-server</artifactId>

```

如果业务系统需要直接读取 SDK 内置资源，可额外引用：

```xml
<dependency>
    <groupId>net.openan.a2a-t.sdk</groupId>
    <artifactId>a2a-t-resources</artifactId>
</dependency>
```

## 1.5 配置加载

Java SDK 不自动发现 `.env`，调用方必须显式传入路径：

```java
import java.nio.file.Path;
import net.openan.a2at.sdk.client.A2ATClient;

A2ATClient client = new A2ATClient(Path.of("client.env"));
```

基础配置示例：

```properties
A2AT_LANGUAGE=zh-CN
A2AT_PROMPT_SOURCE_TYPE=classpath
A2AT_PROMPT_RESOURCE_LOCAL_ROOT_DIR=
A2AT_LLM_PROVIDER=openai
A2AT_LLM_MODEL=deepseek-chat
A2AT_LLM_BASE_URL=https://api.deepseek.com
A2AT_LLM_API_KEY={your_api_key}
A2AT_NEGOTIATION_STATE_STORE_TYPE=in_memory
```

推理模型可选用 `A2AT_LLM_REASONING_EFFORT` 调整传递给提供方的推理力度，取值为 `none`、`minimal`、`low`、
`medium`、`high`、`xhigh` 之一（大小写不敏感）。非推理模型保持该键不设即可——此时不会向提供方发送该参数。
取值不受支持时会在配置加载阶段以 `LLMConfigError` 快速失败，而不是等到首次 LLM 调用才报提供方错误。


## 1.6 SDK 基本用法

### 1.6.1 客户端生成任务提示词

```java
import java.nio.file.Path;
import net.openan.a2at.sdk.client.A2ATClient;
import net.openan.a2at.sdk.client.model.PromptGenerationResult;

A2ATClient client = new A2ATClient(Path.of("client.env"));
PromptGenerationResult result = client.generateTaskPrompt(
        "通知主题为Incident的，订阅条件为：订阅级别为critical的ETH-LOS的故障，上报通知数据格式为：DataPart");

if (result.success()) {
    System.out.println(result.promptText());
} else {
    System.out.println(result.failure().message());
}
```

### 1.6.2 服务端校验任务提示词

```java
import java.nio.file.Path;
import net.openan.a2at.sdk.server.A2ATServer;
import net.openan.a2at.sdk.server.model.PromptComplianceResult;

A2ATServer server = new A2ATServer(Path.of("server.env"));
PromptComplianceResult result = server.checkTaskPrompt(processedPromptText);

if (result.success()) {
    System.out.println("prompt check passed");
} else {
    System.out.println(result.failure().message());
}
```

### 1.6.3 协商接口

```java
import java.nio.file.Path;
import java.util.Map;
import net.openan.a2at.sdk.client.A2ATClient;
import net.openan.a2at.sdk.negotiation.types.model.NegotiationType;

A2ATClient client = new A2ATClient(Path.of("client.env"));
Map<String, Object> payload = client.startNegotiation(
        NegotiationType.INFORMATION,
        "Please provide incident level.",
        Map.of("missingFields", java.util.List.of("subscription_condition_incident_level")));
```

业务系统需要把协商 payload 中的文本和上下文随 A2A 消息传递给对端，后续通过 `receiveNegotiation` 和 `continueNegotiation` 推进状态。


## 1.7 完整集成开发流程

### 1.7.1 客户端 Agent

客户端 Agent 推荐流程：

1. 读取 `.env` 并创建 `A2ATClient`。
2. 根据用户输入调用 `generateTaskPrompt`。
3. 将 prompt 放入 A2A 消息正文或扩展字段。
4. 通过注册中心查询目标 AgentCard。
5. 根据 AgentCard 中的接口地址发起 A2A 请求。
6. 如果收到协商上下文，通过 `receiveNegotiation` 和 `continueNegotiation` 继续交互。

`a2a-t-sample` 中 `subscribe_incident` 用例的 `ClientSampleFlow` 展示了完整流程：读取场景、查询 AgentCard、生成 prompt、构造 A2A 请求并处理流式事件。

### 1.7.2 服务端 Agent

服务端 Agent 推荐流程：

1. 创建业务 HTTP 服务或接入已有 A2A Java 服务框架。
2. 启动时构造 AgentCard 并注册到注册中心。
3. 收到 A2A 请求后提取 processed task prompt。
4. 调用 `A2ATServer.checkTaskPrompt`。
5. 校验通过后执行业务逻辑。
6. 校验失败或信息不足时，通过协商接口返回补充信息要求。

`a2a-t-sample` 中 `subscribe_incident` 用例的 `ServerSampleMain` 和 `ServerSampleFlow` 展示了 AgentCard 注册、HTTP 服务启动、prompt 提取、校验和任务事件推送。

## 1.8 提示词资源扩展
### 1.8.1 文件扩展
自定义场景时，按以下结构准备本地资源：

```text
prompt_resources/
  scenarios/zh-CN/scenarios.json
  slots/{extension_name}/{path_segments}/{version}/zh-CN/slot.json
  templates/{extension_name}/{path_segments}/{version}/zh-CN/template.md
  prompts/scenario_recognition/zh-CN/system.md
  prompts/scenario_recognition/zh-CN/user.md
  prompts/slot_extraction/zh-CN/system.md
  prompts/slot_extraction/zh-CN/user.md
  prompts/semantic_validation/zh-CN/system.md
  prompts/semantic_validation/zh-CN/user.md
```

`slots/` 与 `templates/` 的目录路径与模板 URI 逐段一一对应：`{extension_name}/{path_segments}/{version}` 即模板 URI，`{version}`（默认 `v1`）是末尾段。例如 `energy-saving` 场景对应 `templates/Task-T/network-layer/energy-saving/v1/zh-CN/template.md` 与 `slots/Task-T/network-layer/energy-saving/v1/zh-CN/slot.json`；协商模板则形如 `templates/Negotiation-T/information-negotiation/propose/v1/zh-CN/template.md`。

然后在 `.env` 中指定：

```properties
A2AT_PROMPT_SOURCE_TYPE=local_file
A2AT_PROMPT_RESOURCE_LOCAL_ROOT_DIR={your_prompt_resources_root}
A2AT_LANGUAGE=zh-CN
```

建议为新增资源补充：

1. 场景加载测试。
2. 槽位 Schema 加载和校验测试。
3. 客户端 prompt 生成测试。
4. 服务端 prompt 合规校验测试。
5. sample 级端到端验证。

### 1.8.2 如何定义Prompt模板
#### 1.8.2.1 核心价值
A2A-T 结构化Prompt提供了一种可重复使用的结构化方法，用于为LLM提供明确且一致的提示。通过将核心逻辑与可变数据分离，它使智能体间的交互更加可靠/高效/可扩展。使用结构化Prompt的主要好处包括：
- 	一致性：确保提示遵循标准化格式，从而使得智能体的输出更加可预期。
-	效率：避免从头开始编写每个Prompt，节省了时间和精力。同时，也避免了重复复杂的指令。
-	可扩展性：使得为各种业务场景生成prompt更容易。
-	优化：允许对模板进行改进和优化，从而获得更好的结果。

#### 1.8.2.2 A2A-T Prompt模板的分类
面向电信领域的智能体通信，为保证请求内容的完备性，提高推理效率和准确性，A2A-T面向各个AN高价值场景，定义了结构化Prompt模板，并在TMF发布了产业的A2A-T协议标准：
《IG1453A_Structured_Prompt_of_Agent_to_Agent_Protocol_for_Telecoms_A2AT_v1.0.0》
《IG1453_Agent_to_Agent_Protocol_for_Telecoms_A2AT_v2.0.0》

结构化Prompt模板定义分为两层：
- L0基础模板：
定义ICT领域任务的结构化Prompt的基础框架，不针对特定场景的变量和本体进行具体说明。
L0模板列表：

	| 模板名称 | 说明   |
	|--|--|
	|Task-T  | 定义了ICT领域任务的基本结构，但未针对特定场景规定常用变量和通用本体规范。基础模板的解析依赖LLM的推理能力和Agent的上下文处理能力。 |
	|Notification-T |定义了ICT领域一种结构化的基于提示词的网络事件订阅与报告机制。该机制确保对网络事件进行实时感知，并通过结构化提示，在不同层级、不同领域之间提供一致的任务描述。 |

- L1价值场景Prompt模板：
在L0模板的基础上，为不同高价值场景任务定义了常用的“变量”，以便在任务生成过程中，让智能体能够根据这些变量输入相应的内容，并在任务执行过程中识别相关内容以提高推理效率和准确性。

#### 1.8.2.3 核心组成元素
完整的A2A-T Prompt模板一般包含以下两部分：
1. 指令
	- 定义：核心指示或上下文。
	- 作用：提供任务的基本要求和框架。
	- 语法：使用##直接标记指令名称（如## 任务描述）。
2. 变量
	- 定义：动态槽位，每次使用时填充特定数据。
	- 作用：提供更具体的信息，提升推理效率。
	- 语法：使用双大括号{{}}标识变量名（如{{故障发生时间}}）。

##### 1.8.2.3.1 指令

1. 指令语法要求：在声明“指令”时，应使用“##”进行标记，其后是“指令”的名称，以便Agent能够识别，从而实现内容的输入或相应的推理和执行。
2. 指令集合：A2A-T定义的结构化Prompt已为ICT任务Prompt模板奠定了基础框架，将ICT任务的典型信息解构为以下指令。


|指令名称 | 必选/可选|描述与示例 |
|--|--|--|
| 任务描述 |	必选 	| 描述任务的基本要求。例：<br> `## 任务描述` <br> `请根据“目标对象”、“任务上下文”和“约束条件”分析故障的根本原因，并提供修复建议。请按照“预期输出”中定义的结构回应任务。`
|任务类型|可选  |标识任务类型（如故障诊断、能效优化）。例：<br>`## 任务类型`<br>`故障诊断 ` |
|目标对象|可选|  描述任务操作的直接对象。例：<br> `## 目标对象`<br>`故障标识符（fault-csn）为“OSS-FAULT-20250405-001”。`|
|任务上下文|可选  |提供任务执行的背景信息。例：<br>`## 任务上下文`<br>`故障发生时间（occur-time）为“2025-04-05T14:30:00Z”。 ` |
| 预期输出|可选  | 定义预期结果的格式。例：<br>`## 预期输出`<br> `故障诊断结果应包括以下信息：1. 诊断状态：成功或失败 2. 故障诊断分析结果 3. 修复建议 4. 故障根本原因列表 5. 领域特定信息` |

##### 1.8.2.3.2 变量
1. 变量语法要求：在使用“变量”时，应使用双大括号“{{}}”进行标识，并将变量名置于双大括号内，这样智能体才能识别它，从而实现内容的输入或相应的推理和执行。
2. 变量的实例化方法：变量需要正确实例化才能发挥价值，推荐两种方法
	- 自然语言主谓宾结构：故障发生于2026年1月8日16:38:18
	- key-value简洁格式：故障发生时间：2026/1/8/16:38:18
3. 常用变量集合：
A2A-T基于最佳实践，总结了AN L4高价值场景中常用的变量，这些变量有助于有效描述AN L4高价值场景中的任务：
	|变量名称 | 必选/可选|描述与示例 |
	|--|--|--|
	| 标识符 |	必选 	| 用于指定与任务关联的目标标识符。<br> 例如：<br>`## 目标对象`<br> `{{标识符}}` <br>其实例示例如下： <br>`## 目标对象`<br>`故障标识符（fault-csn）为“OSS-FAULT-20250405-001”。`
	|受影响对象|可选  |用于指定受故障影响的网络资源对象。<br>例如：<br>`## 任务上下文`<br>`{{受影响对象}}`<br>其实例化示例如下：<br>`## 任务上下文 `<br>`受影响对象的ID为“BTS-001”，类型为“基站收发信台”，名称为“基站001”，位置为“北京市朝阳区”。` |
	|相关信息|可选| 其通用本体可以是与故障相关的事件列表或告警列表。<br> 例如：<br>`## 任务上下文 `<br>`{{相关信息}} `<br>其实例化示例如下：<br>`## 任务上下文`<br>`关联告警列表如下：- 告警标识符（alarm-csn）为 "ALM-20250405-001"，告警ID（alarm-id）为 "ALM-001"，告警名称为 "基站信号丢失"，网元名称为 "BTS-001"，告警位置为 "北京市朝阳区"，告警发生时间（alarm-create-time）为 "2025-04-05T14:28:00Z"。- 告警标识符（alarm-csn）为 "ALM-20250405-002"，告警ID（alarm-id）为 "ALM-002"，告警名称为 "传输链路中断"，网元名称为 "TRX-002"，告警位置为 "北京市海淀区"，告警发生时间（alarm-create-time）为 "2025-04-05T14:29:00Z"。`|
	|故障发生时间| 必选 | 其通用本体论是故障发生的时间。<br>例如：<br>`## 任务上下文 `<br>`{{相关信息}}`<br>其实例化示例如下：<br>`## 任务上下文 `<br>`故障发生时间为“2025-04-05T14:30:00Z”。` |
	| 故障上下文对象 | 必选  | 其通用本体可以是来自OSS的故障预处理信息，也可以是来自EMS的告警上报信息。<br>例如：<br>`## 任务上下文`<br>`{{故障上下文对象}}`<br>其实例化示例如下：<br>`## 任务上下文 `<br>`故障上下文对象为：“告警管理系统：FMC，告警位置：北京，告警名称：基站信号丢失，告警时间：2025-04-05T14:28:00Z，告警网元：BTS-001”。` |
    
#### 1.8.2.4 格式和规范
A2A-T中常用文本格式的语法格式规范要求，包括段落、列表、链接，使用Markdown格式确保输出的结构化和可读性：
- 段落：用空行分隔文本块
- 有序列表：数字加句点（1. 项目一）
- 无序列表：破折号开头（- 项目一）
- 链接：方括号加圆括号（[文本](链接)）

##### 1.8.2.4.1 段落
要创建一个段落，可以使用空行将一行或多行文本分隔开。样例：
```
## 任务描述
处理A社区的5G服务故障

完成服务恢复

识别故障的根本原因并进行修复
```

##### 1.8.2.4.2 有序列表
要创建有序列表，需添加以数字加句点表示的条目。这些数字不必按顺序排列，但列表应从数字1开始。样例：
```
## 预期输出 
1. Bar
2. Foo
```

##### 1.8.2.4.3 无序列表
要创建无序列表，请在每行项目前添加破折号（-）。缩进一个或多个项目以创建嵌套列表。样例：
```
## 预期输出
- 项目
  - 项目1
- Bar2
- Foo
```
##### 1.8.2.4.4 链接
要创建一个链接，请在方括号内输入链接文本，然后在其后立即加上用圆括号括起来的网址。样例：
```
## 任务描述
处理[TM Forum AN]（自治网络项目主页）无法加载的问题。
```


#### 1.8.2.5 模板定义的步骤
建议按照如下步骤定义prompt模板：
1.	确定任务类型：明确当前业务场景的任务类型和协作模式，从A2A-T任务分类体系中定位对应的模板类别（如 Task-T）；
2.	编写必要指令：选取关键指令，使用结构化的格式声明任务目标、执行条件、输入参数、预期输出等信息；
3.	填充常用变量：声明本次任务实例所涉及的具体参数，变量引用需要遵循A2A-T变量语法规范；
4.	绑定上下文信息：补充智能体完成任务所需的上下文信息；
5.	设置输出定义：明确定义输出格式、验收标准和异常处理规则；
6.	验证模板完整性：在实际跨模型环境中进行充分测试，验证语法规范性和跨LLM兼容性；
7.	版本迭代优化：将经过验证的模板纳入版本管理体系，便于持续的治理、迭代和演进。

## 1.10 Negotiation-T 内容层

本节介绍 Negotiation-T 内容层：一组以模板为驱动的 API，用于生成协商消息、校验协商消息合规性并从中提取参数。`A2ATClient` 与 `A2ATServer` 均暴露相同的十四个方法。

### 1.10.1 概述与 SDK 边界

内容层覆盖三类能力：

1. **消息生成** — 从类型化数据渲染结构化协商消息（`generateNegotiation*PromptFromData`，确定性执行，不调用 LLM），或从自由文本生成（`generateNegotiation*PromptFromText`，先执行一次 LLM 内容抽取，再确定性渲染）。
2. **合规校验与参数提取** — `validatePromptAndDataFilling*Data` 校验接收到的消息是否为格式正确的协商消息，并按调用方提供的 JSON Schema 提取参数。
3. **模板查询** — `getPrompts` / `getPrompt` 列出和加载当前配置语言下**全部** A2A-T 扩展（Task-T、Notification-T、Authorization-T、Negotiation-T）可用的模板；`getNegotiationPrompts` / `getNegotiationPrompt` 将同样的查询限定在协商模板。

内容层是无状态的。它刻意不持有会话状态机：会话标识、超出消息本身承载范围的轮次跟踪以及角色绑定都由调用方维护。既有的 `startNegotiation` / `receiveNegotiation` / `continueNegotiation` API（见 1.6.3）保持不变，仍是有状态流程的入口；内容层既可以与之组合使用，也可以独立使用。

### 1.10.2 门面方法

以下十四个方法在 `A2ATClient` 和 `A2ATServer` 上具有完全相同的签名和语义。

所有用于标识模板的参数均采用值类型 `net.openan.a2at.sdk.core.model.TemplateUri`，而非裸字符串。`TemplateUri` 恒为格式正确 — 其构造器会校验扩展名、路径段与版本 — 因此格式错误的 URI 不可能进入这些 API。可用 `TemplateUri.of("Negotiation-T", "information-negotiation", "propose")` 构造，更推荐直接使用同包 `StandardTemplates` 中的常量（例如 `StandardTemplates.INFORMATION_NEGOTIATION_PROPOSE`，其 `uri()` 为 `Negotiation-T/information-negotiation/propose/v1`）。当 URI 字符串来自代码之外时，`TemplateUri.parse(String)` 返回 `Optional<TemplateUri>` 且绝不抛出异常。

**从类型化数据生成 — 确定性执行，绝不调用 LLM：**

```java
MetadataContent generateNegotiationProposePromptFromData(NegotiationProposeData data, TemplateUri templateUri)
MetadataContent generateNegotiationAcceptPromptFromData(NegotiationEndingData data, TemplateUri templateUri)
MetadataContent generateNegotiationRejectPromptFromData(NegotiationEndingData data, TemplateUri templateUri)
MetadataContent generateNegotiationAbortPromptFromData(NegotiationAbortData data, TemplateUri templateUri)
```

类型化内容先经过校验，再分发给模板 URI 所指协商类型的生成器，并由该模板渲染。accept 变体要求 `content.conclusion() == ACCEPT`，reject 变体要求 `REJECT`；结论不匹配（包括 `ABORT`）会以 `IllegalArgumentException`（编程错误）拒绝。abort 变体与协商类型无关：它由 `NegotiationAbortData(context, NegotiationAbortContent(terminationReason))` 输入渲染唯一的 common abort 模板 `StandardTemplates.NEGOTIATION_ABORT`，固定的 `Abort` 结论由模板自身承载。

**从自由文本生成 — 一次 LLM 抽取，支持可配置重试：**

```java
MetadataContent generateNegotiationProposePromptFromText(String text, NegotiationContext context, TemplateUri templateUri)
MetadataContent generateNegotiationAcceptPromptFromText(String text, NegotiationContext context, TemplateUri templateUri)
MetadataContent generateNegotiationRejectPromptFromText(String text, NegotiationContext context, TemplateUri templateUri)
MetadataContent generateNegotiationAbortPromptFromText(String text, NegotiationContext context, TemplateUri templateUri)
```

模板在调用 LLM 之前先行加载；模板缺失会快速失败，不会消耗 LLM 请求。LLM 步骤在模板 URI 的约束下从自由文本中抽取类型化内容，随后的渲染与 from-data 变体一样是确定性的。`NegotiationContext` 不经任何 LLM 直接注入生成的 metadata（不再渲染进消息文本）。抽取步骤在可重试错误码（见 1.10.5）上最多重试到配置的尝试上限。abort 变体面向 common abort 模板从自由文本中抽取协商终止原因。

**合规校验与参数提取：**

```java
FilledParamData validateProposePromptAndDataFilling(String prompt, NegotiationContext context, Map<String, Object> schema, TemplateUri templateUri)
FilledParamData validateAcceptPromptAndDataFilling(String prompt, NegotiationContext context, Map<String, Object> schema, TemplateUri templateUri)
FilledParamData validateRejectPromptAndDataFilling(String prompt, NegotiationContext context, Map<String, Object> schema, TemplateUri templateUri)
FilledParamData validateAbortPromptAndDataFilling(String prompt, NegotiationContext context, Map<String, Object> schema, TemplateUri templateUri)
```

流水线按固定顺序执行：

1. 模板 URI 格式检查（phase 段必须与方法匹配：`propose` 或 `accept-reject`）。
2. 确定性规则门禁 — 在任何 LLM 调用之前，校验调用方传入的 `NegotiationContext` 的结构规则（id 为 UUID 形态、轮次不超过轮次预算）；context 为 null 时报 `negotiation_invalid_input`（非协商消息）。
3. 一次 LLM 语义校验调用，同时完成参数提取；在可重试的 LLM 基础设施错误码上最多重试到配置的尝试上限。
4. 将提取的参数与规则层得到的上下文参数合并 — 键冲突时**上下文参数优先**。

**模板查询 — 永不抛出异常：**

```java
List<PromptTemplate> getPrompts()   // 全部扩展在当前配置语言下的模板，按 URI 排序
Optional<PromptTemplate> getPrompt(TemplateUri templateUri)  // 跨扩展按 URI 加载单个模板；未命中返回空

List<PromptTemplate> getNegotiationPrompts()   // 当前配置语言下的全部协商模板，固定顺序
Optional<PromptTemplate> getNegotiationPrompt(TemplateUri templateUri)  // 按 URI 加载单个协商模板；未命中返回空
```

模板缺失时返回空结果并记录 warning 日志；由于入参是已通过校验的 `TemplateUri`，不存在 URI 不可用的情形，null 入参则抛出 `NullPointerException`。`PromptTemplate` 是一个记录类型 `(templateUri, description, content)`，其第一个组件是类型化的 `TemplateUri` 值；`content` 仅在无可加载内容构造模板记录时为 null。泛化查询对直接从内置资源树中发现扩展目录 — 在 `prompt_resources/templates/` 下新增的模板目录（例如未来的 `Authorization-T/`）会被自动列出，无需代码改动。配置的本地资源根目录下的模板会覆盖同路径的内置模板。注意：SDK 尚未打包 Authorization-T 模板资源，`generateAuthPromptFromText` / `generateAuthPromptFromDataWithSchema` 在 classpath 源下会返回 `template_not_found`，直至补充该类模板或通过本地资源根目录提供。

### 1.10.3 模板 URI 与自定义模板

模板 URI 的格式为：

```text
Negotiation-T/{type}-negotiation/{phase}/v1
```

其中 `{type}` 为 `information`、`target` 或 `feasibility`，`{phase}` 为 `propose` 或 `accept-reject`，末尾的 `v1` 是模板版本（默认版本）。门面 API 以类型化的 `TemplateUri` 接收该值；`StandardTemplates` 为每个内置模板提供一个常量。字符串层面的解析绝不抛出异常：`TemplateUri.parse(String)` 返回 `Optional<TemplateUri>`，`NegotiationReference.tryParse` 返回 `Optional<NegotiationReference>` — null、空白或格式错误的 URI（段数、前缀、版本、类型或 phase 段不匹配）只返回空结果。SDK 内置六个模板，每种组合一个，各自提供 `zh-CN` 与 `en-US` 两个语言版本：

| 模板 URI | 用途 |
|--|--|
| `Negotiation-T/information-negotiation/propose/v1` | 请求补充缺失信息 |
| `Negotiation-T/information-negotiation/accept-reject/v1` | 信息协商的接受或拒绝 |
| `Negotiation-T/target-negotiation/propose/v1` | 发起目标协商 |
| `Negotiation-T/target-negotiation/accept-reject/v1` | 目标协商的接受或拒绝 |
| `Negotiation-T/feasibility-negotiation/propose/v1` | 请求可行性评估或提出替代方案 |
| `Negotiation-T/feasibility-negotiation/accept-reject/v1` | 可行性协商的接受或拒绝 |

协商模板采用**双根回退**解析，且该回退与 `A2AT_PROMPT_SOURCE_TYPE` 无关：若 `A2AT_PROMPT_RESOURCE_LOCAL_ROOT_DIR` 配置的本地资源根目录下存在同名模板文件则优先使用，否则回退到内置 classpath 中同一 URI 的模板。内置模板因此始终作为兜底可用。本地根目录用于覆盖模板与协商词表；LLM 提示词资源始终来自 classpath。协商词表遵循同一双根机制：各语言的章节标题、槽位标记名、追加行标签与列表标点位于 `prompt_resources/negotiation-vocabulary/{lang}/vocabulary.json`，在 `{A2AT_PROMPT_RESOURCE_LOCAL_ROOT_DIR}/negotiation-vocabulary/{lang}/vocabulary.json` 放置同名文件即可覆盖内置 classpath 词表；词表文件必须精确定义两个内置语言共同的规范化键集合，否则快速失败。

如需覆盖某个模板（例如中文的信息协商 propose 模板），在本地资源根目录下按内置布局放置文件：

```text
{A2AT_PROMPT_RESOURCE_LOCAL_ROOT_DIR}/
  templates/Negotiation-T/information-negotiation/propose/v1/zh-CN/template.md
```

### 1.10.4 数据模型

所有类型位于 `net.openan.a2at.sdk.negotiation.content` 包。

**NegotiationContext** — 每条协商消息随 metadata 携带的会话上下文，位于 `core.model` 包：`record NegotiationContext(String id, int round, int maxRounds, @Nullable NegotiationPerformative performative)`。它不可变；`nextRound()` 返回轮次加一且 performative 为 `null` 的新上下文（下一条消息的意图尚未决定），`isExhausted()` 判断当前轮次是否严格大于 `maxRounds`，`withPerformative(performative)` 返回盖上给定协商原语的副本。`NegotiationContext.of(id, round)` 使用默认轮次预算 `DEFAULT_MAX_ROUNDS = 5`；三参构造器 `NegotiationContext(id, round, maxRounds)` 的 performative 为 `null`。可选的 `performative` 承担双重角色：输入上下文上它为 `null`——上下文仅作为会话句柄；而生成流水线会在输出上下文上盖戳即将发出的消息的协商原语。

**NegotiationPerformative** — 协商消息的通信意图（协商原语），位于 `core.model` 包：`enum NegotiationPerformative { PROPOSE, ACCEPT, REJECT, ABORT }`。`PROPOSE` 将提案摆上桌面，`ACCEPT` 与 `REJECT` 对提案作出回应，`ABORT` 终止会话；`tryParse(String)` 仅接受精确的大写常量名，其余情况返回空 `Optional`。注意区分 4 个取值的协商原语与模板 URI 的 3 段 phase segment（`propose`、`accept-reject`、`abort`）：协商原语是消息的在线语义，phase segment 则用于定位渲染该消息的模板资源——`ACCEPT` 与 `REJECT` 消息共享 `accept-reject` 这一段。

**输入包装** — `NegotiationProposeData(context, content)` 与 `NegotiationEndingData(context, content)` 将上下文与类型化内容配对，`NegotiationAbortData(context, NegotiationAbortContent)` 将上下文与类型无关的协商终止内容配对。内容类型是按协商类型划分的密封继承体系：

| 协商类型 | Propose 内容 | Ending 内容 |
|--|--|--|
| Information | `InformationProposeContent(List<NegotiationItem> items, String relationship)` | `InformationEndingContent(conclusion, items)` |
| Target | `TargetProposeContent(description, intentUnderstanding, alignmentAndClarification, requestForClarification)` | `TargetEndingContent(conclusion, confirmedIntent, failureReason)` |
| Feasibility | `FeasibilityProposeContent(description, action, contentsToEvaluate, infeasibilityDetailsAndProposal)` | `FeasibilityEndingContent(conclusion, feasibilitySummary)` |

`NegotiationItem(name, value)` 表示条目列表中的一个命名条目。`NegotiationConclusion` 取值为 `ACCEPT`、`REJECT`、`ABORT`；只有 `Accept` 与 `Reject` 是类型化协商模板的可渲染结论 — 类型化生成方法会以 `IllegalArgumentException`（`A2ATError` 树外的编程错误）拒绝 `ABORT`。`ABORT` 结果经由类型无关的 common abort 模板渲染：`NegotiationAbortContent(terminationReason)` 是它唯一携带的内容，`NegotiationAbortData(context, content)` 是其输入包装。`NegotiationAction`（`REQUEST_FEASIBILITY_EVALUATION`、`PROPOSE_ALTERNATIVE_ON_FAILURE`）决定可行性 propose 模板中渲染哪些条件章节。

**MetadataContent** — 生成结果：`record MetadataContent(String templateUri, String promptText, String extensionUri, NegotiationContext negotiationContext)`。`buildMetadataContent()` 返回 `Map<String, Object>`：TMF 扩展 URI（`https://projects.tmforum.org/a2aproject/telecommunication/extensions/Negotiation-T/v1`）映射到渲染后的消息文本，`templateUri` 映射到模板 URI；协商消息额外携带 `negotiationContext` 映射到嵌套的 `{id, round, maxRounds, performative}` 对象——上下文携带协商原语时，`performative` 为其大写常量名（`"PROPOSE"`、`"ACCEPT"`、`"REJECT"`、`"ABORT"`），否则省略该键——非协商消息省略 `negotiationContext` 键、保持两键形态。这个映射即随 A2A 消息 metadata 传输的内容——协商上下文随 metadata 传输，不再渲染进消息文本。

**FilledParamData** — 提取结果：`record FilledParamData(Map<String, Object> data)`，持有上下文参数与按 Schema 提取的参数合并后的结果。

### 1.10.5 错误处理

所有 SDK 处理失败共用同一个根类型，编程错误则留在树外：

- `A2ATError` — **全部** SDK 处理失败（运行期、环境与数据处理失败）的唯一根类型。机器可读错误码声明在根上：`getCode()` 永不返回 `null`，失败没有更具体错误码时携带默认的 `sdk_internal_error`。因此捕获这一个类型即可覆盖 SDK 可能抛出的所有处理失败，包括 LLM 与合规校验失败。
  - `NegotiationProcessingException` — 协商处理失败。
    - `NegotiationGenerationException` — 生成调用抛出。
  - `A2ATParamExtractionError` — 携带结构化槽位错误的参数提取失败；`getCode()` 继承自根，`getErrors()` 返回槽位详情。
    - `NegotiationParamExtractionException` — `validatePromptAndDataFilling*Data` 调用抛出。
  - `LLMError` — LLM 集成失败子树，已并入 `A2ATError` 树。
    - `LLMConfigError` — LLM 配置或提供方注册无效。
    - `LLMRuntimeError` — 调用时的 LLM 基础设施故障。
  - `PromptComplianceCheckException` — 携带错误码与合规阶段（`getStage()`）的合规校验失败；由服务端合规流水线抛出，错误码为 `processed_prompt_parse_error`、`slot_validation_error` 与 `template_not_found`。
  - 其余处理失败 — 提示词生成（`PromptGenerationException`）、内容校验（`ContentValidationException`）、模板渲染（`TaskPromptRenderException`）、资源解析（`ResourceNotFoundException`、`ConfigFileNotFoundException`）、场景识别（`ScenarioRecognitionException`）与协商状态访问（`NegotiationStateException`）— 同属这棵树。

编程错误 — 调用方的入参契约违反 — 刻意留在 `A2ATError` 树外，以标准 JDK 异常抛出，使通用的 `catch (A2ATError)` 处理器无法吞掉它们：null 入参抛出 `NullPointerException`；空白或语义矛盾的入参（上下文 id 为空、传入 `TemplateUri` 构造器的段无效、phase 或结论不匹配、不支持的语言）抛出 `IllegalArgumentException`。原先的 `NegotiationContentException` 已移除；它过去报告的违约现在以这些标准异常形式抛出，各门面方法均以 `@throws` 标签逐一注明。

错误码及其含义：

| 错误码 | 含义 | 可重试 |
|--|--|--|
| `template_not_found` | 任意资源根下都不存在该 URI 的模板（或提示词资源） | 否 |
| `negotiation_content_extract_failed` | 无法从自由文本中抽取结构化内容 | 是 |
| `negotiation_llm_infrastructure_error` | LLM 基础设施故障（网络、提供方错误、响应格式错误） | 是 |
| `negotiation_semantic_rejected` | 语义校验拒绝了该消息 | 否 |
| `negotiation_rule_violation` | 协商上下文违反结构规则 | 否 |
| `negotiation_slot_missing` | 渲染时缺少必需槽位 | 否 |
| `negotiation_invalid_input` | 输入对当前操作无效（FromText 生成调用的输入文本为空、不是协商消息、结论错误） | 否 |
| `param_extraction_failed` | 无更具体错误码时参数提取失败的默认错误码 | 否 |
| `sdk_internal_error` | 无更具体错误码时 SDK 处理失败的默认错误码 | 否 |

重试语义：携带可重试错误码的 LLM 步骤失败后，会重新执行至 `A2AT_LLM_MAX_ATTEMPTS` 配置的尝试上限；携带其他错误码的失败立即原样抛出。尝试次数耗尽时，原始失败以其原始错误码重新抛出。`A2AT_LLM_MAX_ATTEMPTS` 默认值为 3，并被收敛到 1–10 区间（超界值会被收敛并记录 warning 日志）。

### 1.10.6 语言配置

协商模板以及渲染和章节识别所用的词表均按 `A2AT_LANGUAGE` 键控。开箱即用——仅内置 classpath 资源——支持的取值精确地为 `zh-CN` 与 `en-US`；没有任何语言回退，未提供本地词表文件的其他取值在解析词表时会以 `IllegalArgumentException` 失败，错误信息会指向 `A2AT_LANGUAGE`。若本地资源根下存在某语言的有效 `vocabulary.json`，词表层可以完成解析，但除非同时提供该语言的完整模板与 prompt 资源，生成流程仍会在后续以模板缺失失败。

词表本身是文件驱动的：各语言的常量位于 `prompt_resources/negotiation-vocabulary/{lang}/vocabulary.json`，即将 33 个规范化键（章节标题、槽位标记名、追加行标签、列表标点）映射到该语言文本的扁平 JSON 对象。词表遵循与模板相同的双根本地覆盖机制 — `A2AT_PROMPT_RESOURCE_LOCAL_ROOT_DIR` 下存在同名文件则优先，否则回退到内置 classpath 文件；解析过程快速失败、绝不静默降级：词表在两个根下均不存在、无法读取、格式非法或未精确定义规范化键集合时，都会抛出指明语言与文件来源的 `IllegalArgumentException`。因此新增语言仍需完整资源集 — 协商模板与 LLM 提示词资源 — 仅添加词表文件并不足够。请在 `client.env` / `server.env` 中显式设置语言：

```properties
A2AT_LANGUAGE=zh-CN
```

### 1.10.7 端到端示例

以下是一个信息协商的完整示例：客户端发起协商（请求缺失数据），服务端接受并返回数据，两侧均使用内容层：

```java
import java.util.List;
import java.util.Map;
import net.openan.a2at.sdk.client.A2ATClient;
import net.openan.a2at.sdk.core.exception.A2ATParamExtractionError;
import net.openan.a2at.sdk.core.model.StandardTemplates;
import net.openan.a2at.sdk.negotiation.content.*;
import net.openan.a2at.sdk.server.A2ATServer;

// --- 客户端：发起协商，请求两个缺失字段 ---
A2ATClient client = new A2ATClient(Path.of("client.env"));

NegotiationContext context = NegotiationContext.of("neg-0001-uuid", 1);
InformationProposeContent content = new InformationProposeContent(
        List.of(
                new NegotiationItem("subscription_condition.incident_level", "critical or warning"),
                new NegotiationItem("notification_data.format", "DataPart or raw JSON")),
        null);

MetadataContent propose = client.generateNegotiationProposePromptFromData(
        new NegotiationProposeData(context, content),
        StandardTemplates.INFORMATION_NEGOTIATION_PROPOSE);

// 这个映射随 A2A 消息 metadata 传输。
Map<String, Object> metadata = propose.buildMetadataContent();
// metadata.get("templateUri")  -> "Negotiation-T/information-negotiation/propose/v1"
// metadata.get(propose.extensionUri()) -> 渲染后的消息文本
// metadata.get("negotiationContext")   -> 嵌套的 {id, round, maxRounds, performative} 上下文
//                                         （本条消息的 performative 为 "PROPOSE"）

// --- 服务端：校验收到的消息并提取参数 ---
A2ATServer server = new A2ATServer(Path.of("server.env"));

Map<String, Object> schema = Map.of(
        "type", "object",
        "properties", Map.of(
                "subscription_condition.incident_level", Map.of("type", "string"),
                "notification_data.format", Map.of("type", "string")),
        "required", List.of("subscription_condition.incident_level"));

try {
    FilledParamData params = server.validateProposePromptAndDataFilling(
            propose.promptText(), context, schema, StandardTemplates.INFORMATION_NEGOTIATION_PROPOSE);
    // params.data() 持有提取的参数以及上下文参数。
} catch (A2ATParamExtractionError failure) {

}

InformationEndingContent ending = new InformationEndingContent(
        NegotiationConclusion.ACCEPT,
        List.of(new NegotiationItem("subscription_condition.incident_level", "critical")));

MetadataContent accept = server.generateNegotiationAcceptPromptFromData(
        new NegotiationEndingData(context, ending),
        StandardTemplates.INFORMATION_NEGOTIATION_ACCEPT_REJECT);
```
